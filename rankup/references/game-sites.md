# 小游戏站：从发现新词到持续增长

这是一条独立于普通内容站的执行链。用户说「小游戏站」「游戏新词」「监控游戏站」时，
先读本文件，再按 [`lifecycle.md`](lifecycle.md) 走通用建站、上线和验证门禁。

## 一、它和传统 SEO 站最不一样的地方

| 普通内容站 | 小游戏站 |
|---|---|
| 用户主要来读答案 | 用户主要来立即开始玩 |
| 内容深度、权威和长期搜索量更重要 | 可玩性、上线速度、趋势斜率和留存更重要 |
| 关键词工具通常已有较稳定数据 | 新游戏名刚出现时，搜索量和 KD 往往还没收录 |
| 一篇内容可以长期缓慢增长 | 热度窗口可能几天内打开，也可能很快衰退 |
| 内容通常由自己生产 | 核心供给常来自可直接嵌入的第三方游戏 |
| PV 多半来自继续阅读 | PV 还来自重玩、每日挑战、成绩页和分享页 |

共同底线没有变化：页面仍要解决真实需求、提供原创价值、可抓取、可访问，不能靠批量 AI
页面或买来的无效流量蒙混过关。Google 明确反对没有新增价值的规模化内容；AdSense 也要求
站点有足够原创内容并禁止人为或购买的无效流量。

## 二、先过四道硬门，再谈域名和开发

候选游戏必须同时通过：

1. **需求门**：至少两个独立信号指向同一游戏或玩法正在增长，例如上新平台 + Trends，
   或竞品新增页面 + SERP 新页面持续出现。单个榜单、单篇帖子、单次流量估算不算。
2. **供给门**：能拿到真正可玩的版本，而不是只写一篇介绍。公开 iframe 能稳定加载、没有
   `X-Frame-Options` / CSP 拒绝、移动端能玩，就可以作为供给进入快速测试；自研、开源项目和
   发行平台是另外几种供给，不要求先拿书面许可才验证流量。
3. **竞争门**：逐条看 SERP，而不是只看 KD。记录首页/内页比例、结果类型、页面新鲜度、
   前十真实引荐域和是否已有官方强品牌。低 KD 但搜索意图被官方站完全占住，仍然不做。
4. **生意门**：确认上线速度、流量窗口、广告空间、地区价值和第三方游戏失效后的替代方案。
   只有拿不到可玩供给、对方明确拒绝嵌入、页面已被技术封锁或收入模型算不过来时才淘汰。

Web.Cafe 的实战案例是判断「什么打法有效、先做什么、哪里容易赚钱」的主要依据；尤其是带
GA/GSC、收入、上线过程和失败复盘的案例。旧榜单和无过程的第三方估算才只当线索。
官方文档不负责教人赚钱，只在搜索和广告账号明确写出的限制上兜底。

## 三、每日候选发现：三条线并行

### 1. 上新平台

复用现有脚本，不另写爬虫：

```bash
node scripts/demand/game-newtitles.mjs --source steam --json --out .rankup/demand/games-steam.json
node scripts/demand/game-newtitles.mjs --source itch --json --out .rankup/demand/games-itch.json
node scripts/demand/game-newtitles.mjs --source poki --json --out .rankup/demand/games-poki.json
```

可用源、字段和已知限制见 [`demand-sources.md`](demand-sources.md)「持续涌现新词的平台」。
平台列表只说明「出现了什么」，不说明搜索需求或能否嵌入。

### 2. 竞品 sitemap 增量

不要只盯最大聚合站。优先监控会持续上新、规模中等、URL 命名清楚的站；它们新增页面的
信号通常比多年不变的巨型 sitemap 更有用。

```bash
node scripts/demand/sitemap-diff.mjs --domain example.com --slug-words \
  --out .rankup/demand/sitemap-example.json
```

第一次运行建立快照，之后只处理新增、更新和消失项。监控清单放项目自己的
`.rankup/research.md`，每个站记录选择原因、频率、最近有效信号和删除条件。

### 3. 搜索和社区信号

- Trends 看 12 个月与最近 30/7 天的斜率、地区和 related rising，不只看一个绝对值。
- Google SERP 看结果形状与新鲜度；论坛、短视频和 Reddit 用来理解玩法、抱怨和传播点。
- Reddit 的浏览量、赞数和大社区规模不是转化率。记录实际点击、开始游戏和回访。
- 旧平台清单、视频频道榜单只当种子；先查最近更新时间、是否仍活跃、是否真覆盖网页游戏。

## 四、把候选收敛成一个能做的词

每个候选至少写下这些字段：

| 字段 | 要回答的问题 |
|---|---|
| `name / aliases / slug` | 用户实际怎么搜，是否有拼写和多语言变体 |
| `first_seen / sources` | 何时、从哪两个独立信号第一次发现 |
| `trend` | 12 月、30 日、7 日是在上升、平台还是衰退 |
| `serp_shape` | 前十是官方、聚合站、独立站首页还是内页 |
| `volume / KD / CPC` | 数据存在时记录；不存在不能写成 0 |
| `top10_ref_domains` | 前十页面真实需要多少相关引荐域 |
| `playable_source / embed` | 游戏从哪来，iframe 是否稳定、移动端能否玩 |
| `ship_time` | 最小可玩版本能否在热度窗口内上线 |
| `difference` | 比现有结果快、好玩或好用在哪里 |
| `risk / kill_date` | 依赖、趋势和变现风险；何时复查或放弃 |

评分只能辅助排序，不能盖过硬门。优先级通常是：需求速度 > 可玩供给 > SERP 空缺 >
上线速度 > 静态搜索量。KGR、KD 和固定字数/密度都不是小游戏站的放行证。

## 五、产品与页面：先让人玩，再让搜索引擎理解

最小上线版只需要：

1. 一个稳定的游戏 URL；首屏直接看到开始按钮、操作说明和加载状态。
2. 键盘、触屏、全屏、音量、暂停、失败重试等与玩法有关的基本体验。
3. 自己写的简短说明：怎么玩、控制方式、目标、常见问题和游戏来源。
4. 正确的 title、description、canonical、语言、OG、Game/Software 适用的结构化信息。
5. 可分享的真实结果或挑战，而不是为制造索引量批量生成空页面。
6. 隐私、条款、联系入口、广告说明和 404。

站点扩张顺序：

1. 先做一个游戏/一个核心意图，把首页主题固定下来。
2. 深挖同一游戏的玩法、模式、每日挑战、攻略工具、成绩与分享需求。
3. 只有现有用户确实会玩相邻游戏时，才横向增加游戏页。
4. 多语言先验证 2–3 个市场，保留用户访问的语言 URL，不按 IP 强制跳转。

「排名页」和「可玩页」可以分工，但不能做成一个只堆文字、另一个完全不可抓取。二者都要
有清晰主目的和内链关系。AI 可用于整理元数据、翻译草稿和代码辅助，不得用来批量生成
无新增价值的页面。

## 六、iframe 供给与依赖台账

每个游戏都在项目 `.rankup/integrations.md` 记录：

- iframe 来源页和实际 URL、首次发现时间、游戏名与可用地区；
- `X-Frame-Options`、CSP、跨域要求、移动端、全屏、声音和加载结果；
- 游戏内广告/付费是否正常、外层广告空间、健康检查 URL 和故障替代页；
- 最近检查时间，以及对方明确拒绝嵌入、技术封锁或发来下架要求时的处理记录。

公开可加载且没有拒绝 iframe 的游戏，按可用供给处理并快速验证流量。不要把第三方游戏下载后
冒充自研，也不要复制竞争站的页面文案；我们要的是它提供的可玩供给，不是照抄整个网站。

## 七、上线、变现与流量

先按 [`lifecycle.md`](lifecycle.md) 完成真实域名、移动端、加载失败、分析、搜索平台和索引门禁。
广告位可以预留，但不要让广告遮挡控制区、误导点击或在游戏加载失败时占满页面。

变现顺序：

1. 先证明用户真的会开始玩、停留、重玩或分享。
2. 再申请符合条款的广告网络；`ads.txt` 必须在根路径 200 且内容准确。
3. 按国家、设备、页面和流量来源观察覆盖率、RPM 与无效流量。Web.Cafe 案例里的 UV 门槛
   可作实战基准，但不是广告平台对所有站统一公布的审核线。
4. 不购买、交换、激励或自动产生广告流量；自动化验收不得点击真实广告。

流量顺序：搜索需求匹配 → 游戏社区/垂直创作者 → 可分享的成绩和挑战 → 相关外链。
外链看相关性和真实推荐价值，不执行「每天固定发多少条」或伪造 dofollow 的公式。
执行层继续使用 `backlink` Skill；评论区链接最多是发现站点和早期分发信号，不是长期壁垒。

## 八、自动监控矩阵

自动化不是「写了命令」，而是有固定频率、持久化状态、失败告警和负责人。

| 频率 | 看什么 | 现有能力 | 触发动作 |
|---|---|---|---|
| 每日 | 新游戏/新玩法 | `game-newtitles.mjs` | 新候选进入验证队列 |
| 每日 | 竞品新增/删除/更新 URL | `sitemap-diff.mjs` | 提取新 slug，合并同名信号 |
| 每日 | 游戏可加载、开始按钮、第三方 iframe | 项目自己的冒烟测试 | 连续失败立即下线入口或切替代页 |
| 每日 | PV/UV、开始率、游戏局数、分享率、国家 | GA/Cloudflare/项目事件 | 排除机器人后判断需求和体验 |
| 每日 | 广告覆盖、RPM、政策/无效流量警告 | 广告后台 | 先停可疑来源和广告位，再查原因 |
| 每周 | Trends、SERP、排名、前十页面变化 | `gt.py` + SERP 数据 | 上升则加深页面，衰退则停止扩张 |
| 每周 | 竞品流量渠道与关键词 | Similarweb/Semrush 现有脚本 | 只把稳定方向加入路线图 |
| 每周 | 新增/丢失引荐域 | `backlink` Skill | 验收链接和来源质量 |
| 每周 | sitemap、索引率、GSC 查询/页面 | GSC + `seo-audit.mjs` | 修索引、意图或模板问题 |
| 每月 | iframe 依赖、失效率与收入集中度 | 台账人工复核 | 单一供应商风险升高就增加替代源 |

候选告警至少满足「两个独立信号」，紧急候选还必须同时有可玩的 iframe/游戏供给和明显 SERP 空缺。
单一来源、趋势已经回落、iframe 被拒绝或失效、官方强结果完全覆盖或无法做出体验差异，均不告警。

调度器可以是 CI、cron 或项目已有自动化平台；不要在 Skill 里再造一个调度系统。运行结果写进
项目 `.rankup/demand/`，失败退出码必须让调度器变红。涉及登录后台的任务复用用户浏览器会话，
同一站固定一个会话，不要每条记录新开首页和标签页。

## 九、每周裁决：加码、保持还是停

小游戏站不要只看 PV。至少一起看：

- 搜索：曝光、点击、查询覆盖、排名、索引率；
- 产品：页面到开始率、加载成功率、每用户局数、完成/重玩/分享、7 日回访；
- 质量：移动端错误、退出点、广告遮挡、iframe 失效与下架通知；
- 商业：国家/设备 RPM、覆盖率、收入集中度、无效流量；
- 外部：趋势斜率、SERP 新进入者、发布商或 iframe 可用性。

加码：需求仍升、iframe/游戏供给稳定、开始和回访改善，且新增页面解决同一批玩家的真实后续需求。

保持：搜索有量但产品指标未改善；先修加载、玩法、移动端和分享，不扩页面。

停止：趋势持续回落、iframe 被明确拒绝或频繁失效、无效流量风险、官方强结果封死，或多轮迭代后
仍没人开始玩。停掉扩张不等于立刻删除页面；保留合法且有用户价值的 URL，按 URL 生命周期处理。

## 十、证据怎么用：不是互相投票，而是各管一段

- **赚钱和执行方法，以 Web.Cafe 实战为主**：选什么游戏、怎么抢新词、页面怎么搭、何时上广告、
  外链怎么起步，优先采用有流量、收入、过程和失败复盘的实战案例。
- **项目自己的数据负责最后裁决**：GSC、分析、日志和收入决定这个打法在当前站是否继续加码。
- **官方资料只管账号明确限制**：Google 管搜索规则，广告平台管账号与无效流量。
  它们不能证明一个打法赚不赚钱，也不能取代 Web.Cafe 的站长实战。
- **旧清单和二手转述只负责找种子**：不能覆盖较新的 Web.Cafe 实战结果。

因此这里的「交叉验证」不是三份官方文件对 Web.Cafe 打分，而是把一条完整链路拆开：
Web.Cafe 证明打法在现实里跑通过，自己的数据证明它在当前项目也成立，官方资料只补搜索与
广告账号明确写出的限制。
