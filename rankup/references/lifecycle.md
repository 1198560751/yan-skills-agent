# 网站全生命周期

本文件是 `rankup` 的执行工作流。它把网站从机会判断到长期经营拆成阶段 `0` 到 `10`。阶段是导航，不是必须从头重跑的瀑布流程：已有网站先完成阶段 0 的事实对账，再从与当前目标最相关的阶段进入；不得为了套流程而重新初始化、迁移或覆盖已有项目。

所有输出路径均相对于项目根目录。写入 `.rankup/` 前先遵循项目记忆协议；任何密钥真实值都不得写入 `.rankup/`、Git、日志或命令输出。

## 通用执行规则

1. 每次只推进能用当前证据验收的最小工作单元。
2. `.rankup/` 是项目记忆，不是实时事实源。涉及代码、Git、Cloudflare、Stripe、搜索平台或线上状态时，必须重新读取真实来源。
3. 每个阶段都必须满足可观察门禁才算完成。生成文件、构建成功、Worker 上传成功或口头确认都不能替代门禁。
4. 如果门禁失败，在 `.rankup/audit.md` 或当日日志记录证据与下一步，保持该阶段未完成。
5. 真实生产变更遵循最小范围和可回滚原则；破坏性操作必须取得用户对确切目标和环境的授权。

## 阶段 0：恢复并对账项目上下文

### 输入

- 用户当前目标和约束。
- `.rankup/INDEX.md`、`.rankup/PROJECT.md`、`.rankup/skill-state.json` 及任务相关主题文件。
- 当前工作树、Git 历史、应用代码、配置和相关线上服务。

### 必做动作

1. 判断是绿地项目、已有项目还是一次专项修复。
2. 读取 `.rankup/INDEX.md` 推荐的最小文件集合；目录不存在时初始化项目记忆。
3. 检查工作树、近期提交、实际目录和运行脚本，避免覆盖用户改动。
4. 对任务涉及的 Cloudflare bindings、域名、部署、数据库、对象存储、支付或搜索状态进行实时核对。
5. 修正已确认过期的项目记录，并标明证据时间；不确定项标为待验证。
6. 检查 `rankup` 版本状态，但 Skill 更新不得修改业务代码或部署网站。

### 输出

- `.rankup/INDEX.md`
- `.rankup/PROJECT.md`
- `.rankup/skill-state.json`
- 必要时更新 `.rankup/plan.md`、`.rankup/audit.md` 和 `.rankup/journal/<date>.md`

### 完成门禁

能用当前代码、Git 和相关线上来源说明项目的真实状态、当前目标、未提交改动、目标环境和下一阶段；项目记忆中的冲突已修正或明确标记为待验证。

## 阶段 1：机会与市场调研

### 输入

- 项目目标用户、场景、约束与商业目标。
- 搜索需求、趋势、竞品、社区反馈和可获得的真实交易信号。
- 已有站点的流量、转化、收入和客户反馈（如有）。

### 必做动作

1. 定义目标用户、核心痛点、现有替代品和愿意付费的结果。
2. 收集需求、竞争、可切入缺口和商业信号，并标注来源与日期。
3. 使用 `D+C+W+M` 机会门禁评估需求、竞争、切口和变现，不以单一搜索量或技术可行性代替完整判断。
4. 明确最小验证版本、成功指标、失败阈值、成本和主要风险。
5. 有 SEO 或趋势任务时读取 SEO 参考并调用对应专业 Skill。

### 输出

- `.rankup/PROJECT.md`
- `.rankup/baseline.md`
- `.rankup/keywords.md`
- `.rankup/decisions.md`
- `.rankup/plan.md`

### 完成门禁

每个进入开发的机会都有带来源的需求证据、竞争判断、可验证切口、商业路径、最小范围和量化的继续/停止标准；证据不足的候选保持 `RESEARCH`，不得伪装为已验证机会。

## 阶段 2：产品与架构设计

### 输入

- 通过阶段 1 门禁的机会或已有网站的明确变更目标。
- 用户旅程、内容需求、非功能要求、预算、合规和运营约束。
- 已有代码与基础设施（如有）。

### 必做动作

1. 定义产品范围、非目标、关键页面、用户路径和验收标准。
2. 设计 Monorepo 边界、TanStack Start SSR/API、数据模型、鉴权、支付、内容与分析方案。
3. 按真实需求选择 Cloudflare 资源，不为猜测中的未来需求预建复杂设施。
4. 区分 preview、staging、production 的资源、域名、数据和发布策略。
5. 定义数据迁移、失败恢复、可观测性与回滚路径。
6. 记录重要选项、依据、代价和被否决方案。

### 输出

- `.rankup/architecture.md`
- `.rankup/infrastructure.md`
- `.rankup/integrations.md`
- `.rankup/decisions.md`
- `.rankup/plan.md`

### 完成门禁

关键用户路径和验收标准可测试；每个选用的 Cloudflare 服务都有明确需求、binding、环境边界和失败处理；高风险数据、支付和发布动作均有迁移或回滚方案。

## 阶段 3：初始化项目

### 输入

- 已批准的产品和架构设计。
- 目标目录、包名、运行环境及本机 Node.js/pnpm 状态。
- 现有目录和 Git 状态。

### 必做动作

1. 仅对确认的绿地目录运行默认脚手架命令；已有项目不得重新初始化：

   ```bash
   pnpm dlx shadcn@latest init --preset b1D0eCA4 --template start --monorepo --rtl --pointer
   ```

2. 检查实际生成的应用与共享包、workspace 配置、TanStack Start 入口、TypeScript 配置和包管理器脚本。
3. 安装后执行类型检查、测试和生产构建中当前可用的项目命令。
4. **审计脚手架的产物路径配置**（见下「脚手架四个坑」第 1 条）。
5. **把站点自身的身份装上去**：`<html lang>` 用目标市场语言、title/description/og 用目标语言实文案、
   404 页本地化、首页替换成真实落地页。**不要留 `Project ready!` / `Hello world` 这类占位**——
   它会一路活到上线，而且没人会专门回来改。
6. **初始化版本控制与远端**（见下「Git 与远端」）。
7. 将实际结构与初始架构记录对账，不假定模板输出永远不变。

### 脚手架四个坑（每一条都实际踩过）

1. **产物目录与缓存配置对不上，表现为构建缓存永不命中。**
   预设的构建编排配置里写死的输出目录，可能与当前构建工具版本的实际产物目录不同
   （模板更新滞后于构建工具升级是常态）。症状是每次全量重建，外加一条
   `no output files found for task` 的**警告**——警告不是错误，于是被无视很久。
   **判据：脚手架跑通后立刻连跑两次构建，第二次必须命中缓存。** 没命中就去核对输出目录配置。

2. **脚手架的 `init` 会交互式追问项目名，并把项目建成一个子目录。**
   非交互环境下它会挂在提示符上直到超时。用它的 `--name` 参数跳过。
   而「建成子目录」这一条决定了**目标目录已经有内容时（例如已有项目记忆目录）不能就地初始化**：
   要先在别处生成，再把内容搬进去。
   **搬运时排除依赖目录**——跨文件系统的 `mv` 等于全量复制，几百 MB 白搬；
   到位后重新安装依赖，是秒级操作。

3. **暗色模式默认不跟随系统。** 主流组件库预设按类名切换主题，
   而不是 `prefers-color-scheme`，需要一个 theme provider 才生效。
   **必须实测**：把浏览器配色切到 dark 看页面变不变。不测就会把「预设支持暗色」
   当成「这个站支持暗色」，两者不是一回事。

4. **预览/开发服务配置的工作目录是会话的主工作目录，不是项目子目录。**
   在父目录下管多个项目时，直接写包管理器命令会在父目录里执行并报一个
   指向**完全无关的另一个项目**的 `ENOENT`——错误信息把人带向错误的方向。
   用包管理器的「指定目录」参数把目录显式写进启动参数里。

### Git 与远端

**脚手架跑通、类型检查与构建都过之后，立刻建仓并推远端**，不要等「做出点东西再说」。
理由是这个阶段的产出（脚手架版本、预设参数、你为修坑做的改动）恰恰是最难凭记忆重建的，
而它此时只存在于一台机器上。

1. 脚手架通常会自带一个本地仓库与一条初始提交，**先确认，不要重复 `git init`**。
2. **提交前扫一遍将要入库的内容**：令牌、密钥、账号配置、代理地址一律不得入库；
   确认忽略规则覆盖依赖目录、构建产物与本地环境文件。
3. 建远端仓库。**默认私有**：未上线项目的仓库里通常带着选题、竞品调研与定价策略，
   公开等于把选题送人。要公开必须是用户明确要求。
4. 项目记忆目录**随仓库一起提交**——它是这个项目最贵的资产，留在单机上没有意义。
   例外仍然是那条老规矩：跨项目资产登记表与真实凭据永不入库。

### 输出

- 项目 Monorepo 源码与配置。
- **一个有远端的 Git 仓库**，脚手架状态已推送。
- `.rankup/architecture.md`
- `.rankup/decisions.md`
- `.rankup/journal/<date>.md`

### 完成门禁

生成目录与目标目录一致，Monorepo 的应用和共享包可被包管理器识别，TanStack Start 的开发/构建脚本真实可运行，
用户已有文件没有被覆盖，**连续两次构建第二次命中缓存**，**站点身份已是目标市场语言而非模板占位**，
且**远端仓库存在、当前状态已推送**。

## 阶段 4：建立 Cloudflare 全栈基础

### 输入

- 已验证的项目结构与架构。
- Cloudflare 账户、目标环境和非敏感资源标识。
- 数据、对象、异步任务、一致性和密钥需求。

### 必做动作

1. 按 `cloudflare-stack.md` 将 TanStack Start SSR/API 接入 Workers 和 `@cloudflare/vite-plugin`。
2. 按需创建并绑定 D1、R2、KV、Queues、Workflows 或 Durable Objects；不用 KV 保存事务事实。
3. 为 preview、staging、production 分配隔离资源并核对 binding 名称。
4. 每次变更 bindings 后运行 `wrangler types`，让应用类型与真实配置一致。
5. 为 D1 建立迁移并分别验证目标环境；真实密钥只进入 Worker Secrets、Secrets Store 或 CI secrets。
6. 建立本地开发、预览、部署、观测和回滚命令。

### 输出

- Worker、Wrangler、bindings 和迁移配置。
- `.rankup/infrastructure.md`
- `.rankup/secrets.md`（仅密钥元数据）
- `.rankup/architecture.md`
- `.rankup/decisions.md`

### 完成门禁

本地或预览环境能够执行真实 SSR/API 路径；所有声明的 bindings 均可被类型检查并完成最小读写验证；环境资源没有意外交叉；密钥扫描确认仓库和 `.rankup/` 中不存在真实密钥值。

## 阶段 5：开发与测试

### 输入

- 可执行计划、验收标准、架构和已配置的开发/预览环境。
- 当前测试、类型检查、lint 和构建命令。

### 必做动作

1. 将功能拆成小步实现，每步先定义可观察结果。
2. 覆盖核心业务逻辑、API、SSR、水合、数据访问、权限和错误路径。
3. 对 D1 迁移、R2 上传、异步处理和环境差异做集成验证。
4. 运行类型检查、单元测试、集成测试和生产构建；不得隐瞒失败或把不相关旧失败归因于本次改动。
5. 对关键页面与交互做真实浏览器或等价端到端验证。

### 输出

- 业务代码与测试。
- `.rankup/audit.md`
- `.rankup/plan.md`
- `.rankup/decisions.md`
- `.rankup/journal/<date>.md`

### 完成门禁

目标验收场景通过，相关回归检查和生产构建通过；未解决问题有明确证据、影响和处置计划；关键路径不仅由 mock 或 fixture 证明。

## 阶段 6：集成专项能力

### 输入

- 已确定的支付、邮件、分析、鉴权、搜索、AI 或其他外部能力需求。
- 对应供应商环境、专业 Skill 和验收条件。

### 必做动作

1. 优先发现并调用专业 Skill；支付使用 Stripe 指南，Cloudflare 操作使用 Wrangler/Workers 指南，能力缺口使用 `find-skills`。
2. 记录非敏感资源 ID、模式、环境、webhook 路径、权限范围和负责人。
3. 密钥真实值只写入批准的 secret store；项目文件仅记录名称和存放位置。
4. 分别验证成功、失败、重试、幂等、权限拒绝和供应商超时路径。
5. 支付资源必须用目标环境凭证核对 test/live 模式、金额、币种和周期。

### 输出

- 集成代码与测试。
- `.rankup/integrations.md`
- `.rankup/secrets.md`（仅元数据）
- `.rankup/decisions.md`
- `.rankup/audit.md`

### 完成门禁

集成在目标环境完成端到端验证；回调签名、幂等和错误路径有证据；资源模式与环境一致；代码、日志、Git 和 `.rankup/` 均未暴露密钥值。

## 阶段 7：部署并真实线上验证

### 输入

- 通过测试的精确提交或构建产物。
- 目标环境、Wrangler 配置、迁移计划、域名和回滚版本。
- 关键路径检查清单。

### 必做动作

1. 部署前确认精确 Git SHA、目标环境、bindings、待执行迁移、域名和回滚点。
2. 先完成迁移与依赖检查，再使用 Wrangler 部署指定环境。
3. 上传完成后等待部署进入可服务状态，并从真实域名验证 SSR HTML、静态资源、API、D1、R2 上传/读取、鉴权和支付回调。
4. 对边缘缓存或传播延迟进行有界重试，并用版本标识、响应头或实际内容确认服务的是新版本。
5. 检查日志与错误率，保存部署标识、时间、验证证据和回滚命令。

### 输出

- 已发布的线上版本。
- `.rankup/releases.md`
- `.rankup/audit.md`
- `.rankup/infrastructure.md`
- `.rankup/journal/<date>.md`

### 完成门禁

目标部署可通过 Cloudflare 部署状态关联到预期提交；真实域名返回预期 SSR HTML，关键 API 和实际 bindings 正常，上传、鉴权及适用的支付回调已验证；回滚目标和方法已记录。仅有构建成功、Worker upload 成功或健康页 `200` 不算完成。

## 阶段 8：SEO 与内容增长

### 输入

- 真实线上页面、站点结构和当前技术/内容基线。
- GSC、Bing、分析、SERP、抓取、转化和业务数据。
- 机会池与目标受众语言。

### 必做动作

1. 读取 SEO 增长参考，先核实数据渠道和时间窗口。
2. 检查可抓取性、索引、canonical、robots、sitemap、结构化数据、性能和多语言信号。
3. 用真实查询、页面和转化证据排序机会，每轮只实施少量高置信变更。
4. 构建、部署后从线上 HTML 和搜索平台验证生效，不以本地产物替代边缘结果。
5. 记录变更前基线、观察窗口和回看日期。

### 输出

- `.rankup/baseline.md`
- `.rankup/keywords.md`
- `.rankup/audit.md`
- `.rankup/experiments.md`
- `.rankup/plan.md`

### 完成门禁

目标页面的线上技术信号与内容变更已核实，搜索平台操作有可追踪状态，实验拥有变更前基线、目标指标和回看日期；不能承诺尚未经过观察窗口的排名或流量结果。

## 阶段 9：分发与外链

### 输入

- 已上线且可交付价值的页面或产品。
- backlink 分析、竞品链接、目录、媒体、社区与合作伙伴机会。
- 目标受众、地区、品牌和合规约束。

### 必做动作

1. 使用 `backlink` 的分析参考评估链接质量、相关性、可达性和风险。
2. 使用 `backlink` 执行经授权的目录提交、触达和跟进。
3. 逐项核对结果 URL、确认状态、审核要求、费用和错误信息；通用成功文案只能产生待复核候选。
4. 避免垃圾链接、误导性资料、重复提交和不透明付费方案。
5. 将已确认、待审核、失败、拒绝和下一步分别记录。

### 输出

- `.rankup/integrations.md`
- `.rankup/experiments.md`
- `.rankup/plan.md`
- `.rankup/journal/<date>.md`

### 完成门禁

每项分发都有目标、执行证据、实际结果 URL 或明确审核状态和下一步；不得把表单提交、成功关键词命中或待付费页面报告为已获得有效外链。

## 阶段 10：监控、学习与迭代

### 输入

- 发布、实验、SEO、分发、收入、成本、可靠性和用户反馈。
- `.rankup/` 历史记录及当前线上事实。

### 必做动作

1. 按约定周期检查技术健康、索引、流量、转化、收入、成本和用户反馈。
2. 将异常定位到具体版本、页面、渠道、环境或集成，避免只看聚合指标。
3. 更新实验结果、决策、待办和发布记录；压缩陈旧日志并维护 `INDEX.md`。
4. 下一轮开始前重新完成阶段 0 对账，不把历史勾选框当成当前状态。
5. 项目事实只留在项目 `.rankup/`；仅将跨项目、重复验证且不含敏感信息的知识提升到 Skill。

### 输出

- `.rankup/INDEX.md`
- `.rankup/baseline.md`
- `.rankup/experiments.md`
- `.rankup/releases.md`
- `.rankup/plan.md`
